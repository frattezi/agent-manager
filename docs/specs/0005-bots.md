# Spec 0005: Bots

Status: accepted (2026-11-27). Vocabulary: [GLOSSARY.md](../../GLOSSARY.md). Decision:
[ADR 0006](../adr/0006-bots-configured-here-knowledge-versioned-in-fractory.md). The commands a
Bot drives are Spec 0006 in `frattezi/fractory`.

## Goal

The owner keeps starting the same conversation. Something is wrong with the factory, or the
machine is loaded, or a Run has been sitting for a day, and they open a session, re-explain
what Fractory is, re-explain which commands answer the question, and then ask it. The
explanation is identical every time and costs context every time. When they want two of those
conversations at once — one watching Runs, one watching the machine — they set the same thing
up twice.

A Bot Profile is that setup, stored once. The owner picks it from a Bots area and gets a Bot: an
ordinary Session, already specialized, already knowing which commands are its eyes and hands,
already remembering what earlier Bots from the same Profile worked out. They talk to it the way
they talk to any session — "CPU is pegged, raise the parallelism", "watch this for an hour and
adjust", "what has been stuck longest" — and it answers by running commands, not by reasoning
from a prompt.

The first Profile is an operator specialized in keeping Fractory running. It is not the point.
The point is that the second one costs a row.

## Non-goals

- **Triggers, schedules and anything that wakes a Bot.** A Bot is conversational: it acts when
  the owner opens one and asks. Reacting to a state change without being asked is what
  Fractory's Triggers and Runs are for, and an Automation already covers work on a clock.
- **A new execution path.** A Bot is a Session. Nothing new runs it, nothing containerizes it,
  nothing writes a request for Fractory.
- **A hardcoded Profile.** No Profile ships in `builtinTools` or anywhere else in code. The
  area starts empty and the owner creates what they want, because a frozen personality is the
  same defect as a frozen model.
- **A Claude-only feature.** A Profile names a tool and a model from what the manager discovers
  the CLI offers. The orchestrator will be Claude on Opus; the mechanism does not care.
- **Putting the Specialization in the store.** What a Bot knows is a committed skill in the
  Fractory repository. The Profile names it. A text area in a dialog is not where knowledge
  that deserves review and history goes.
- **A permissions model of its own.** A Bot launches with the flags its Profile carries, like
  an Automation. The manager does not decide what an agent may do.
- **Rendering A2UI surfaces.** A Bot answers in prose, and a Findings table is rendered by
  `fractory doctor`. An Agent Surface in the manager is its own Spec, if it is ever one.
- **Sharing memory between Profiles.** Each Profile remembers in its own place.

## Solution

**The Profile.** A row in Settings, stored in `state.db`: a name, an emoji and a colour, the
tool and the model, the directory a Bot starts in, the launch flags, the Specialization it
loads, and the ai-memory project it remembers in. Created and edited in a dialog the way the
Automations dialog works, and readable and writable from a shell with `agent-manager bots`, so
the manager, the CLI and the MCP server all see the same rows. A value that is a command or a
token stays off the dialog, as every other setting of that kind does.

**The area.** Bots get their own section in the list, below Automations, so they never crowd
what the owner is working on. Each Profile is a row carrying its emoji and colour, its name and
its tool; unfolding it lists the live Bots spawned from it, each an ordinary session row with
the status the poller already gives it. Selecting a Profile fills the detail column with its
configuration and its live Bots; selecting a Bot shows the session it is.

**Spawning.** A key on a Profile row starts a Bot: a Session in the Profile's directory, under
the Profile's group, running the Profile's tool and model, launched with its Specialization
already in the system prompt. Several Bots may run from one Profile at once, each named so the
owner can tell them apart. A Bot is attached to, focused, previewed, renamed, killed and
archived like any other Session, because it is one.

The Specialization and the memory project reach the Bot as configuration, never as something
the Bot is asked to do. The Specialization is passed as a system prompt file on the launch
command; the memory project is bound by an `.ai-memory.toml` in the Bot's own directory, which
ai-memory reads from the nearest marker. Neither spends a turn, neither decays with compaction,
and both return on every relaunch, because launch flags persist where a first prompt does not.

The flag that carries a system prompt file is **not** named in the Bots package. It is a field
on the tool definition, set for every CLI that has one, so a Bot specializes on whichever CLI
the Profile runs and a CLI without the capability simply starts unspecialized.

**Memory.** One ai-memory project per Profile, bound by an `.ai-memory.toml` in the Bot's
directory. Every Bot from that Profile recalls what the others concluded; a Bot spawned
tomorrow starts where today's left off. Reads of a specific repository's knowledge go through
ai-memory's named scopes, which needs nothing from the manager.

The marker is written only into a directory the Profile owns, never into a repository the owner
works in: an `.ai-memory.toml` in a real checkout would re-scope memory for every agent that
runs there, not just this Bot. A Profile whose directory is a repository inherits that
repository's memory scope instead, which is the right answer for a Bot that works inside it.

**The Specialization.** A skill the Profile names, found at a Fractory-managed repository's
`.agents/skills/<name>/SKILL.md`, else at the global `~/.claude/skills/<name>/SKILL.md`. The
repositories are every checkout the Run registry names, the ones the Runs rail reads, searched
in path order; the Fractory home holds state, not a checkout, and is never one of them. The
manager passes that path through the CLI's `append_system_prompt_flag`, after the Profile's own
flags, so it is part of the session's launch flags and a revive keeps it. The file is passed by
path, never read or copied, so the next Bot gets whatever the skill says by then. A name that
resolves to no file is an error at spawn and starts nothing; on a CLI with no such flag the Bot
starts without it. It carries what the operator knows: that `fractory doctor` is its eyes, that
`fractory limits` shows and sets Host Limits with ranges it cannot exceed, that
`fractory tokens` says what Runs cost, and when each applies. It carries no step with a right
answer: anything computable is in those commands.

Every key here has a click, every clickable surface has a key, and both appear in the footer
and under `?`.

## User stories

1. As the owner, I want to describe a specialized agent once, so that starting one does not mean re-explaining Fractory.
2. As the owner, I want to start several Bots from one Profile, so that one can watch Runs while another watches the machine.
3. As the owner, I want each Profile to carry an emoji and a colour, so that I can tell my Bots apart in the list at a glance.
4. As the owner, I want a Bot to be an ordinary session I can attach to, so that everything I already know about driving a session still applies.
5. As the owner, I want every Bot from a Profile to share its memory, so that what one worked out is not lost when I close it.
6. As the owner, I want to tell a Bot "raise the parallelism" and have it happen, so that adjusting the factory is a sentence rather than a file edit.
7. As the owner, I want a Bot's knowledge to live in git, so that it is reviewed and versioned like the rest of the factory.
8. As the owner, I want to pick the tool and model per Profile, so that a better model next quarter is a dropdown and not a release.
9. As the owner, I want the Bots area below Automations, so that it never pushes my working sessions down the list.
10. As the owner, I want to edit a Profile and have the dialog open on what is stored, so that changing a colour is not re-entering everything.
11. As the owner, I want `agent-manager bots` from a shell, so that a Profile can be inspected without opening the TUI.
12. As the owner, I want a Profile with no live Bots to cost nothing, so that keeping several around is free.

## Implementation decisions

- **A new `internal/ui/bots` package**, added to `tools/architecture/check-file-names`, with
  root adapters named `bots_adapter*.go`, `bots_*_effect.go` and `bots_*_surface.go`, following
  the Settings and Automations adapters exactly. The package never imports the root.
- **A new migration at the end of the `internal/store` slice**, written so re-running it is
  harmless, holding one table for Profiles. Nothing existing is altered.
- **Every Profile field is in `ui.SettingSpecs`** with the values it takes, so
  `agent-manager bots` refuses what the dialog would never write.
- **The tool and model lists come from the manager's existing capability discovery**, the same
  source the spawn picker uses. No list of models is written down.
- **Spawning reuses the session creation path** the spawn picker and the MCP server already
  call. A Bot differs from any other session only in the prompt it starts with and the Profile
  it records, so the poller, the preview, focus mode and archiving need nothing.
- **A Bot records its Profile id**, which is how the area groups live Bots under their Profile.
  A Profile deleted while Bots run leaves them running and ungrouped; they are ordinary
  sessions and the owner closes them when done.
- **The colour comes from the theme's palette**, chosen by index, never a hex value, so a Bot
  stays legible in every theme.
- **A Bot's context is configuration, not instruction.** The Specialization rides the launch
  command as a system prompt file and the memory project is bound by a marker file. Asking a
  model to load its own context spends a turn, cannot be verified, decays with compaction and
  is lost on revive; configuration has none of those failure modes. This is No Token
  Architecture applied to a Bot's identity. Recorded in
  [ADR 0008](../adr/0008-a-bots-context-is-configuration-not-a-first-prompt.md),
  which supersedes the first-prompt mechanism this Spec originally described.
- **The system prompt file is the skill file in git.** Nothing is copied or inlined at spawn, so
  editing the skill changes what the next Bot is, with no migration and no release.

## Testing decisions

- **Store** (`internal/store`): the migration runs on a fresh database and on an upgraded one;
  Profiles round-trip; a Profile is read identically by two processes.
- **Dialog and area** (`internal/ui/bots/*_test.go`): the dialog opens empty for a new Profile
  and on stored values for an edit; a refused field is reported against that field; the area
  renders a Profile row, an unfolded Profile with live Bots, and an empty area; every key has a
  row-menu entry and appears under `?`; every clickable surface has a key.
- **CLI** (`main_test.go`): `agent-manager bots` lists, shows, creates and edits; a value
  outside its `SettingSpecs` entry is refused.
- **Spawning** (`internal/ui`): a spawn from a Profile creates one session with the Profile's
  tool, model, directory and group, and records the Profile id; two spawns from one Profile
  both run and group together.
- **Against real sessions**, as a UI change requires: build the binary, run it under a
  throwaway `HOME` on its own socket, create a Profile, spawn two Bots from it, and read the
  frames back. A green suite is not that.

## Open questions

- Whether a Profile should be exportable, so the same Bot can be set up on another machine.
  The Specialization travels in git already; the row does not. Deferred until there is a second
  machine.
- Whether a Bot should be able to spawn another Bot. The session tools exist, and the owner's
  standing rule is that only they decide when sessions work together, so no for now.
- Whether the Bots area belongs in the rail at all once there are many Profiles, or whether it
  becomes a picker. One Profile does not answer that.
